# null_blk 기반 ZNS SSD 동작 실습 및 ZUFS 사례 분석

## 개요

이 문서는 ZNS SSD의 Zone 기반 데이터 관리 구조를 이해하고, 기존 SSD와의 성능 및 쓰기 처리 방식 차이를 실습으로 확인한 내용을 정리한다. 또한 Zoned UFS 사례를 통해 Zone 기반 기술이 모바일 스토리지 환경에서 어떻게 확장될 수 있는지 살펴본다.

## 실습 환경

실습은 Linux Kernel 5.18.0 기반의 QEMU 가상화 환경에서 진행했다. 스토리지 성능 측정과 워크로드 생성에는 `fio`를 사용하고, NVMe 디바이스 제어와 상태 확인에는 `nvme-cli`를 사용했다. Zone 상태 조회와 Zone 관리 명령 수행에는 `blkzone`을 활용했다.

## 실습 구성

### Lab 1: ZNS SSD의 쓰기 제약 확인 및 기본 성능 비교 측정

두 장치에 동일한 순차 쓰기 워크로드를 인가하여 처리량과 평균 지연 시간을 측정한다. 이후 ZNS SSD에 랜덤 쓰기 워크로드를 인가하여 순차 쓰기 제약을 위반했을 때 발생하는 오류를 확인한다.

### Lab 2: ZNS SSD의 Zone 상태 조회 및 제어

`blkzone` 명령어를 통해 각 Zone의 상태와 Write Pointer 위치를 조회하고, 쓰기 작업에 따라 Zone 상태가 어떻게 변화하는지 관찰한다. 명시적인 Open 명령 없이 쓰기를 수행했을 때 Zone이 자동으로 Open 상태로 전이되는지도 확인한다. 이후 특정 Zone에 대해 Open, Write, Close, Finish, Reset 과정을 순서대로 수행하며 Write Pointer 이동과 Zone 상태 변화를 분석한다.

### Lab 3: ZNS SSD와 Conventional SSD의 WAF 비교 측정

실험은 F2FS 환경에서 진행한다. `null_blk`는 실제 SSD의 NAND, FTL, device-side GC를 포함하지 않기 때문에 파일시스템 및 block layer 수준에서 관찰 가능한 host-visible write 기반의 간접 지표를 측정하기 위함이다.

먼저 conventional 모드와 zoned 모드의 `null_blk` 장치 위에 각각 F2FS를 구성하고, 동일한 워크로드를 수행한다. 이후 워크로드 수행 전후의 `write_sectors` 변화량을 측정하여 호스트가 요청한 쓰기 양과 block layer에서 관찰된 쓰기 양을 비교한다. 이를 바탕으로 conventional 모드와 zoned 모드에서 쓰기량이 어떻게 다르게 나타나는지 비교하고, 예상한 WAF 경향과 실제 측정 결과 사이에 차이가 발생하는 원인을 분석한다.

### Lab 4: ZNS 기술이 모바일 스토리지에 확장된 Zoned UFS 논문 스터디

Conventional UFS는 논리 주소와 물리 주소 매핑을 위해 큰 규모의 SRAM을 필요로 하지만, Zoned UFS는 순차 쓰기 제약을 활용해 매핑 테이블 크기를 줄일 수 있다. 또한 Android, F2FS, 블록 레이어, 드라이버, 장치 펌웨어가 협력하는 크로스 레이어 최적화 구조를 분석한다.

마지막으로 Zoned UFS가 단편화가 심한 환경에서도 기존 UFS보다 높은 쓰기 처리량을 유지하는 원리를 살펴본다. WAF 감소가 스토리지 수명 연장과 사용자 체감 성능 향상에 미치는 영향도 함께 평가한다.

## 실습 결과

### 1회차: ZNS SSD 동작 실습

스터디 페이지를 참고하며 ZNS SSD의 기본 개념을 복습한 뒤 실습을 진행했다. 실습에 필요한 모듈을 설치하려면 DPAS 패치를 적용한 Linux 5.18.0 커널 소스를 직접 빌드한 환경이 필요했다.

참여자별 커널 빌드 환경과 모듈 경로가 달라 동일한 실습 환경을 즉시 재현하기 어려웠다. 따라서 1회차에서는 준비된 환경의 실행 결과를 함께 확인하고, 이후 개별 재현이 가능하도록 실습 페이지를 보완했다.

실습 환경은 기존에 구성되어 있던 QEMU와 Linux 5.18.0 커널을 기반으로, 여기에 `null_blk`, `f2fs` 모듈을 설치한 뒤 가상 conventional SSD와 ZNS SSD를 1 GB씩 구성했다.

#### Lab 1 결과

첫 번째 실습에서는 conventional SSD와 ZNS SSD의 순차 쓰기 성능을 비교했다. `fio`를 이용해 두 장치에 순차 쓰기를 실행했으며, ZNS SSD인 `nullb1`은 730 MiB/s와 평균 지연 시간 319.71 us를 기록했고, conventional SSD인 `nullb0`은 620 MiB/s와 평균 지연 시간 303.71 us를 기록했다. 처리량은 ZNS SSD가 더 높게 나왔지만 평균 지연 시간은 conventional SSD가 약간 낮았기 때문에, 두 장치의 순차 쓰기 성능 차이가 일관된 우위로 나타났다고 보기는 어려웠다.

일반적으로 ZNS SSD는 GC가 줄어들기 때문에 성능상 이점이 드러날 수 있지만, 이번 실습은 가상 환경에서 진행되었기 때문에 실제 SSD에서 발생하는 GC 비용이 충분히 반영되지 않았다. 따라서 순차 쓰기 성능 비교만으로는 ZNS SSD의 장점이 명확히 드러나지 않았다. 또한 실행 환경의 성능 부하에 따라 기존에 측정해 둔 출력 결과보다 처리 시간이 크게 증가하는 모습도 확인할 수 있었다.

이후 랜덤 쓰기 실습을 통해 ZNS SSD의 쓰기 제약을 확인했다. conventional SSD에서는 랜덤 쓰기가 496 MiB/s로 정상 실행되었지만, ZNS SSD에서는 `write offset=65564672, buflen=4096` 위치의 쓰기 요청에서 `Input/output error`가 발생했다. 커널 로그에서도 `dev nullb1, sector 128056`에 대한 쓰기 I/O 오류가 확인되었다. 이는 ZNS SSD가 zone 내부에서 순차 쓰기만 허용하기 때문이다. 이 실습을 통해 ZNS SSD의 핵심 특징이 단순한 이론적 설명이 아니라 실제 명령 실행 결과로도 확인할 수 있음을 보여주었다. 다만 ZNS SSD에서도 랜덤 쓰기와 유사한 동작이 필요한 경우에는 F2FS와 같은 소프트웨어 계층에서 이를 처리할 수 있다.

#### Lab 2 결과

두 번째 실습에서는 존 상태와 존 관리 명령을 확인했다. `blkzone` 명령을 통해 각 존의 상태, 크기, write pointer의 위치를 확인했다. 초기 상태에서는 존들이 비어 있는 상태였고, write pointer도 시작 위치에 있었다. 이후 별도의 Open 명령 없이 Zone 0에 32 MB 쓰기를 수행하자 395 MiB/s의 처리량을 보였고, write pointer는 `0x010000`으로 이동했으며 해당 존의 상태는 빈 상태에서 암시적 오픈 상태인 `oi`로 전환되었다. 이때 전체 16개 존 중 15개 존은 `em`, 1개 존은 `oi` 상태였다. 별도의 오픈 명령을 실행하지 않아도 쓰기 요청이 들어오면 자동으로 존이 열리는 방식이 implicit open이다.

explicit open 실습에서는 쓰기 전에 명령을 통해 존을 미리 열어두는 방식을 확인했다. 이 경우 Zone 1은 `oe` 상태로 열렸지만 실제 데이터가 쓰이지 않았기 때문에 write pointer는 `0x000000`에 머물렀다. 이후 32 MB 쓰기를 수행하자 681 MiB/s의 처리량을 보였고, write pointer가 `0x010000`까지 이동했으며 존 상태는 `oe`로 유지되었다. close 명령을 수행하면 존은 `cl` 상태가 되지만 write pointer는 `0x010000`으로 유지된다. 이는 남은 공간이 있는 경우 이후 쓰기가 기존 write pointer 위치부터 다시 진행되어야 하기 때문이다. 반면 finish 명령은 존을 더 이상 쓸 수 없는 완료 상태인 `fu`로 만들기 때문에 write pointer가 `0x020000`까지 이동한다.

존 리셋 실습에서는 완료 상태였던 존이 다시 빈 상태로 돌아가는 과정을 확인했다. 리셋 전에는 Zone 1이 `fu` 상태였고, `blkzone` 출력상 해당 존은 `start=0x000020000`, `len=0x020000`, `wptr=0x020000`으로 표시되었다. 리셋을 수행한 뒤에는 write pointer가 해당 존의 시작 위치로 돌아가며 출력상 `wptr=0x000000`, 상태 `em`으로 바뀌었다. 전체 리셋을 수행하면 16개 존이 모두 빈 상태로 복원되었다. 이를 통해 존 리셋은 단순히 파일을 지우는 수준이 아니라, 존을 다시 사용할 수 있도록 초기화하는 명령임을 확인했다.

#### Lab 3 결과

세 번째 실습에서는 WAF 측정을 시도했다. 배경 지식상 ZNS SSD는 WAF가 1에 가까울 것으로 예상했고, conventional SSD는 1보다 큰 값이 나올 것으로 가정했다. 그러나 이번 환경에서는 실제 SSD의 FTL과 NAND 내부 쓰기 동작을 직접 관찰할 수 없었기 때문에, F2FS와 블록 레이어에서 관찰 가능한 host-visible write를 이용해 WAF와 유사한 값을 간접적으로 측정했다.

측정 결과는 예상과 다르게 나타났다. conventional SSD에서는 `fio`가 발생시킨 논리 쓰기량이 48.00 MiB였고, `write_sectors` 변화량으로 계산한 device write는 48.11 MiB였다. 따라서 host-visible WAF는 `48.11 / 48.00`에 해당하는 1.002로 1에 가까운 값이 나왔다. 반면 ZNS SSD에서는 `fio` 논리 쓰기량이 256.00 MiB였지만, `write_sectors` 변화량으로 계산한 device write는 10855.29 MiB였고, host-visible WAF는 42.403으로 크게 나타났다. 이 결과는 ZNS SSD의 실제 WAF를 의미하는 것이 아니다. 이번 측정은 FTL 내부에서 발생하는 실제 쓰기 증폭을 본 것이 아니라, F2FS 단에서 관찰 가능한 쓰기량을 본 것이기 때문이다.

conventional SSD는 호스트 입장에서 덮어쓰기가 가능한 블록 장치처럼 동작하므로, 이번 측정 방식에서는 추가적인 파일시스템 계층 쓰기 증폭이 크게 드러나지 않았다. 실제로 conventional SSD에서는 F2FS GC 호출 증가가 없었고, 이동된 블록 수도 0으로 나타났다. 반면 ZNS SSD는 순차 쓰기 제약 때문에 제자리 덮어쓰기가 불가능하고, 유효 블록을 다른 존으로 복사한 뒤 기존 존을 리셋하는 과정이 필요하기 때문에 파일 시스템 계층에서 더 큰 쓰기량이 발생했다. 측정 중 ZNS SSD에서는 F2FS GC 호출이 336회 증가했고, 이동된 블록 수는 2,744,319개로 나타났으며, 결과적으로 ZNS SSD 쪽의 값이 더 크게 나타났다.

이 실험은 ZNS SSD의 device-internal WAF를 직접 측정하지는 못했지만, `null_blk`/F2FS 환경에서 관찰 가능한 지표와 실제 SSD 내부 WAF가 다르다는 점을 확인하는 데 의미가 있었다. 정확한 측정을 위해서는 FTL을 직접 조절하거나 관찰할 수 있는 다른 에뮬레이션 환경이 필요하다.

#### 1회차 주요 논의

ZNS SSD의 핵심은 FTL의 내부 동작을 호스트나 애플리케이션 단에서 일정 부분 제어할 수 있도록 하는 데 있다. 따라서 F2FS 환경에서 host-visible WAF를 측정하는 것이 어떤 의미를 갖는지에 대한 논의가 있었다.

이번 실습은 기존 QEMU 환경을 유지한 상태에서 진행되었기 때문에 FTL 수준의 동작까지 다루지는 못했다. 따라서 ZNS의 본래 목적을 완전히 반영한 실습이라고 보기는 어렵다. WAF를 보다 정확하게 측정하기 위해서는 FTL 단을 직접 제어하거나 관찰할 수 있는 환경이 필요하며, 이를 지원하는 다른 에뮬레이터 환경을 활용할 필요가 있다.

### 2회차: ZUFS 논문 스터디

논문 발표자료를 바탕으로 ZUFS의 구조와 성능 평가 내용을 정리했다. ZUFS는 모바일 저장장치인 UFS에 zone 개념을 도입한 방식이다. 모바일 기기에서 스토리지 성능은 앱 로딩 시간, 일시적인 렉, 사용자 경험에 직접적인 영향을 주며, 저장해야 하는 데이터의 양이 계속 증가하고 있기 때문에 스토리지 안정성이 중요해지고 있다. 현재 UFS는 대부분의 스마트폰에서 표준 저장장치로 사용되고 있지만, 필요한 저장 용량과 읽기 성능은 증가하는 반면 최대 전력량과 SRAM 크기는 크게 늘어나지 못한다는 한계가 있다.

이 한계로 인해 발생하는 첫 번째 문제는 큰 매핑 테이블 부담이다. 플래시 스토리지는 데이터를 제자리에 덮어쓸 수 없기 때문에 논리 주소와 물리 주소를 매핑해야 하며, 페이지 단위 매핑을 사용할 경우 매우 큰 매핑 테이블이 필요하다. 예를 들어 1 TB 스토리지에서는 페이지 수준 매핑 시 약 1 GB의 매핑 테이블 저장 공간이 필요할 수 있고, 모바일 기기는 SRAM이 제한적이기 때문에 이 부분이 병목으로 작용할 수 있다.

두 번째 문제는 단편화이다. 스마트폰을 오래 사용할수록 파일 생성, 삭제, 갱신이 반복되면서 완전히 비어 있는 segment는 줄어들고, 유효 데이터와 무효 데이터가 섞인 dirty segment가 증가한다. 이로 인해 읽기 및 쓰기 지연 시간이 증가하고, 실제 스마트폰 사용 환경에서도 장기 사용 후 단편화가 성능 저하로 이어질 수 있다.

이후 ZUFS가 이러한 문제를 어떻게 해결하는지 정리했다. ZUFS는 스토리지를 여러 zone으로 나누고, 각 zone 내부에서는 쓰기 작업을 순차적으로 수행하도록 강제한다. 이를 통해 페이지 수준 매핑 대신 zone 단위 매핑을 사용할 수 있으며, 1 TB 기준 매핑 테이블 크기를 약 1 GB에서 약 8 KB 수준으로 줄일 수 있다. 또한 내부 GC에만 의존하지 않고 호스트가 zone 관리를 수행한다.

다음으로 ZUFS 구현에서 발생하는 주요 과제들을 살펴보았다. 첫 번째 과제는 여러 zone을 동시에 열어두고 각 zone의 상태를 관리해야 한다는 점이다. 기존의 static buffer 방식은 zone마다 고정 크기 버퍼를 배정하기 때문에 일부 zone은 버퍼가 낭비되고, 특정 zone에는 버퍼가 부족해질 수 있다. host-managed 방식 역시 운영체제나 파일 시스템이 디바이스 내부 상태를 정확히 알기 어렵기 때문에 버퍼를 반복적으로 회수하고 재할당하는 thrashing 문제가 발생할 수 있다.

이 문제를 해결하기 위해 ZUFS는 ZABM, 즉 Zone Aware Buffer Management를 사용한다. ZABM은 디바이스 내부에서 zone 사용 패턴을 고려해 버퍼를 동적으로 할당하는 방식이다. 이를 통해 제한된 SRAM 환경에서도 버퍼 공간을 효율적으로 사용하고, 순차 쓰기 성능을 안정적으로 유지할 수 있다.

두 번째 과제는 쓰기 순서 보장이다. ZUFS는 zone 내부에서 엄격한 순차 쓰기가 필수적이지만, 모바일 환경에서는 전력 관리나 유휴 상태 복귀 과정에서 요청 처리 순서가 흔들릴 가능성이 있다. 이에 대해 블록 계층과 드라이버를 수정해 이벤트를 추적하고 ordering을 보장하는 방식으로 순차 쓰기 조건을 유지한다.

이와 관련해 모바일 UFS가 유휴 상태에서 복귀할 때 클럭 제한이나 정상화 과정으로 인해 패킷 순서가 꼬일 가능성이 있고, 이로 인해 Zoned UFS의 순차 쓰기 보장이 깨질 수 있다는 논의가 있었다. Zoned UFS는 순차 쓰기가 깨지는 순간 zone 기반 관리의 의미가 약해질 수 있으므로, 이 부분이 구조적 단점이 될 수 있다는 의견을 정리했다.

세 번째 과제는 GC이다. ZUFS는 zone 크기가 크기 때문에 GC가 발생하면 많은 양의 데이터를 이동해야 하고, 이 과정이 사용자의 foreground I/O를 지연시킬 수 있다. 따라서 공간이 부족해질 때까지 기다리는 방식이 아니라, 백그라운드에서 선제적으로 GC를 수행하는 Proactive GC를 통해 foreground I/O 정지를 줄이고 반응성을 개선한다.

성능 평가 부분에서는 CUFS와 ZUFS의 순차 쓰기, 랜덤 쓰기, 단편화 상황에서의 지연 시간, 애플리케이션 수준 성능을 비교했다. 순차 쓰기 성능은 큰 차이가 없었지만, 랜덤 쓰기에서는 저장 용량이 증가해도 ZUFS가 비교적 안정적인 모습을 보였으며, 이를 통해 랜덤 쓰기 허용 여부만으로 성능을 판단하기 어렵다는 점을 논의했다.

또한 여유 공간이 부족한 상태에서 단편화 영향을 확인한 결과, 기존 스토리지는 GC와 버퍼 경합으로 지연 시간이 높고 불안정해진 반면 ZUFS는 ZABM과 Proactive GC를 통해 더 안정적인 지연 시간을 유지했다. 마지막으로 게임 로딩 시간 단축과 갤러리 앱 jank 감소 등 실제 사용자 경험 지표에서도 ZUFS의 개선 효과를 확인했다.

#### 2회차 주요 논의

ZNS SSD와 ZUFS는 모두 zone 기반 순차 쓰기를 활용하지만, ZNS SSD는 NVMe SSD 환경을 전제로 하고 ZUFS는 모바일 UFS 환경을 전제로 한다는 차이가 있다. 또한 ZUFS는 제한된 전력, SRAM, 발열, Android/F2FS 구조를 고려해야 하므로 cross-layer 설계가 중요하다.

Zone Append의 경우 디바이스가 실제 쓰기 위치를 결정한다. 반면 ZUFS는 host가 write pointer와 쓰기 순서를 직접 관리하는 host-managed 순차 쓰기 모델을 전제로 하므로, 디바이스가 기록 위치를 결정하는 Zone Append 방식과 맞지 않는다. 마지막으로 ZUFS의 관리는 대부분 OS, F2FS, 블록 계층, 스토리지 펌웨어에서 이루어지므로 앱 개발자가 직접 다루는 부분은 적지만, 앱의 I/O 패턴은 체감 성능과 단편화에 영향을 줄 수 있다.

## 정리 및 한계

이번 실습에서는 `null_blk`와 QEMU 기반의 가상 환경을 사용했기 때문에 실제 SSD 내부에서 발생하는 FTL 동작, NAND Flash의 device-side GC, 실제 WAF 변화를 직접 관찰하기는 어려웠다. 따라서 기대했던 성능 차이나 WAF 감소 효과가 실험 결과에서 명확하게 드러나지는 않았다. 향후에 ZNS의 실제 WAF와 GC 감소 효과를 더 정확히 확인하려면 FTL 동작을 직접 제어·관찰할 수 있는 에뮬레이터를 활용해 검증할 필요가 있다.

또한 ZUFS 논문을 통해 기존에 알고 있던 Zone 기반 구조가 모바일 스토리지 스택에서 어떻게 구현되고 활용되는지 구체적으로 이해할 수 있었다. 특히 랜덤 쓰기 처리, Zone 상태 관리, 데이터 배치, Zone 회수 과정에서 발생하는 문제를 어떤 방식으로 줄이려 하는지 확인할 수 있었고, ZNS의 장점을 실제 사용자 경험 개선으로 연결하는 과정을 정리할 수 있었다. 파일시스템, 블록 계층, 드라이버, 펌웨어가 함께 동작하는 광범위한 크로스 레이어 설계가 필요하므로 구현 복잡도 역시 크다는 점도 확인했다.

이 실습은 ZNS를 이론이 아니라 실제 시스템 관점에서 바라보는 데 초점을 둔다. 동시에 가상 장치 기반 검증에서는 실제 SSD 내부 동작을 충분히 관찰하기 어렵다는 한계도 함께 드러났다.
